# 학교 Wi-Fi에서 세 명이 만나기까지

2026년 11월, 작은 2D 방에서 시작해 **같은 학교 Wi-Fi에 연결한 친구가 실제로 내 노트북의 방에 들어올 수 있는지** 확인했다. 이후 웹 브라우저 간 직접 연결과 LAN 호스트 방식의 전달 비용을 별도로 측정했다.

## 1. 호스트는 응답하는데 Safari에서 열리지 않았다

11월 18일 첫 eduroam 실험에서 친구 기기가 페이지를 열지 못했다. 당시 자료만으로 eduroam 실패 원인은 확인할 수 없었다. 팀은 KNU-WiFi6로 옮겨 구간별로 다시 검사했다.

| 관찰 | 조치와 결과 |
| --- | --- |
| 방장 노트북에서 광장 페이지와 `/health`가 HTTP 200을 반환했다. | 서버가 동작 중임을 확인했다. 친구의 Safari에서 같은 응답을 받는지 따로 확인했다. |
| 두 기기가 같은 SSID에 연결됐지만 호스트는 세 번째 옥텟이 66인 대역, 친구는 72인 대역을 받았다. | 실험용 Windows 방화벽 수신 규칙은 호스트와 같은 /24만 허용하고 있었다. 친구 주소가 그 범위 밖인 것을 찾았다. |
| 프로젝트 전용 규칙의 허용 대상에 그 친구를 추가했다. | Safari에서 페이지를 열고 입장했다. 호스트에서도 해당 기기의 페이지 요청·입장·상태 구독을 확인했다. |
| 팀은 이 장비 조합에서 팀원 3명이 통신했다고 보고했다. 참가자가 늘 때마다 새 주소를 등록하면 운영이 어려웠다. | 이후 참가자 IP를 한 명씩 등록하는 절차를 없앴다. 허용 범위는 게임 전용 실행 파일·현재 Wi-Fi 인터페이스·호스트의 로컬 주소·해당 TCP 포트로 계속 한정했다. |

시험 중 학교 네트워크 장비 설정은 변경하지 않았다. 현장의 성공 범위는 당시 기기와 네트워크 조합이다. 주소를 따로 받는 학교망에서는 두 기기가 같은 SSID라는 사실만으로 접속 여부를 판단하기 어렵다.

## 2. 웹 직결이 멈춘 구간

웹판의 WebRTC 연결은 참가자 발견, 연결 제안과 응답 교환, 경로 후보 검사, 데이터 채널 열기의 순서를 따른다. 한 현장 시도에서 두 기기는 각각 상대의 제안·응답을 적용했고 후보 쌍도 한 개씩 표시했다.

| 기기 | 경로 검사 송신 | 응답 수신 | 상태 |
| --- | ---: | ---: | --- |
| PC | 121 | 0 | checking |
| 휴대폰 | 201 | 0 | checking |

이 기록에서 확인한 것은 **관찰된 후보 쌍의 왕복 확인이 완료되지 않았다**는 점이다. 수치는 브라우저 통계이므로 어느 AP·방화벽·NAT가 원인이었는지는 판별할 수 없다. 직접 연결이 성립하지 않는 참가자는 [웹 연결 모드](https://knu-direct-plaza.vercel.app/?mode=web)를 선택할 수 있다. [W3C WebRTC 통계 정의](https://www.w3.org/TR/webrtc-stats/)

## 3. 이동 정보를 모두에게 보내는 비용

LAN 클라이언트는 행동을 HTTP로 보내고, 호스트는 SSE로 방의 변경 사항을 전달한다. 짧은 시간에 발생한 이동을 모아 보내고, 공부 화면에 집중하는 사람에게는 화면 밖 캐릭터의 이동 갱신을 줄였다. [구현](../src/server.mjs) · [32명 비교 스크립트](../scripts/load-spaces.mjs)

초기 비교에서는 한 노트북에서 모의 참가자 32명이 각자 **초당 8회, 10초간** 이동을 요청했다. 두 경우 모두 2,560건의 이동 요청이 성공했다. 모든 사람이 캠퍼스 화면을 구독할 때 받은 SSE 본문은 **32.52 MiB**, 16명이 공부 화면을 구독할 때는 **15.65 MiB**였다. 두 값은 같은 송신 부하에서의 구독 조건 비교이며 초기 지도 다운로드는 제외했다. 서버와 부하 생성기가 같은 프로세스에서 실행됐다.

## 4. 행사판의 정원 100명과 모의 연결 검증

메인 광장은 100명까지 입장할 수 있다. 이동을 짧은 주기로 묶고 바뀐 캐릭터 정보만 보내며, 재입장한 클라이언트에는 전체 상태를 전달한다. 행사판은 별도 서버와 부하 생성기를 한 노트북의 루프백에 연결했다. 10초 측정값은 다음과 같다.

| 접속한 모의 참가자 | 이동한 참가자 | 성공한 이동 요청 | 이동 요청 지연 p95 | 서버 SSE 본문 송신률 |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 10 | 800 | 8.4 ms | 2.61 Mbit/s |
| 100 | 100 | 8,000 | 64.9 ms | 24.43 Mbit/s |

100명 모두의 채팅 수신, 101번째 입장의 만석 응답(HTTP 409), 자리 하나가 비면 새 참가자의 입장과 최근 채팅 복구를 확인했다. 별도 검사에서는 실제 Chromium 창 하나와 모의 참가자 99명으로 친구 목록 100/100, 원격 캐릭터 99개, 이동과 양방향 채팅을 확인했다. [100명 측정 스크립트](../scripts/load-event-plaza.mjs)

현장 증거는 선행 버전에서의 팀원 3명 통신이다. 모의 100명 시험은 무선 구간, 휴대폰 100대의 첫 화면 다운로드, 프레임 속도나 장시간 발열을 측정하지 않는다. 현장에서는 서로 다른 모바일 기기로 먼저 입장과 상호작용을 확인하고 참가자 수를 늘려야 한다.
